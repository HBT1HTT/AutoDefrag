# 整理设置分组 + Defraggler 同级整理能力评估（方案稿）

> 本文只给方案，不含代码改动。所有“现状”结论均来自当前仓库代码，关键位置已标注。

## 0. 结论摘要

1. **设置分组可行**。建议在“整理方式”下方新增“整理设置”卡片，把现有“整理范围”里的碎片率阈值迁进去，再加 5 个真正影响结果的偏好项。
2. **门控建议：本程序整理 = 可编辑；Windows 自带整理 = 整组置灰；自动 = 也置灰**（保留已保存的值，切到“本程序整理”后生效）。理由见 2.2。
3. **与 Defraggler 同级要拆开看**：在 HDD 上，对“被选中的数据文件”可以做到每个文件 1–2 个区段、文件级碎片率接近 0；但**整卷碎片率、空闲空间碎片、MFT/系统锁定文件不可能同级**，那不是参数问题，是能力缺口。
4. 现有“碎片率”只统计**已分析文件**，覆盖率可能只有几个百分点；拿它和 Defraggler 的整卷数字直接比会失真。见 3.1。
5. 建议分三阶段：P1 设置与迁移 → P2 多轮整理与速度 → P3 HDD 空闲空间合并。启动期系统文件整理、MFT/元数据整理**不建议做**。

- `MinFileClusters = 8` 是**按卷簇大小折算**的（`VolumeAnalyzer.cs:43-49`）。在 64KB 簇的盘上等于 512KB，这才是大簇盘覆盖率低的主因。
- 每次任务只处理一批，没有“处理完再选下一批”的循环；40 文件/8GB 就是**单次任务上限**。

## 2. 需求一：「整理设置」分组

### 2.1 位置与结构

- 位置：放在“整理方式”卡片下方，原“整理范围”卡片（只有碎片率阈值）整体迁入，原卡片删除，避免两组设置语义重叠。
- 结构建议：
  - 卡片标题「整理设置」，副标题说明“只对内置引擎的文件级重写生效；参数在下次整理开始时读取”。
  - 第一行：只整理碎片率较高的文件（开关 + 阈值，沿用现有绑定与错误提示）。
  - 分隔线以下为「高级偏好」：最小文件大小、单轮文件数、单轮数据量、可回收下限、校验强度。
  - 对话框已有 `ScrollViewer`（`SettingsWindow.xaml:27`），新增约 5 行不会撑破布局；窗口 560×640，滚动条兜底。
- 每个高级项都带一句“默认值/范围”说明，沿用现有 `HintText` 样式；非法值不保存，保存按钮统一校验（与现有阈值一致，`SettingsWindow.xaml.cs:296-342`）。

### 2.2 门控规则

| 整理方式 | 「整理设置」状态 | 说明文字 | 理由 |
|---|---|---|---|
| 本程序整理（Self） | 可编辑 | “这些参数只对文件级重写生效；小于 4KB 簇的盘仍走 Windows 自带整理，不受影响。” | 唯一会读这些参数的路径 |
| Windows 自带整理（System） | 整组置灰 | “这些参数只对内置引擎有效；当前选择 Windows 自带整理，参数不会生效。” | 系统 defrag 不读阈值/批大小；可编辑会造成“调了没用”的错觉 |
| 自动（Auto） | **整组置灰** | “自动模式按每块盘的存储块大小选择：只有大簇盘用内置引擎，小簇盘仍走 Windows 自带整理。切到「本程序整理」后可编辑。” | 同意用户的倾向。自动模式下参数只在部分盘生效，若可编辑会让人误以为全盘生效；保留已保存值，切换后立即可用 |

补充两点：

- **即使选 Self，也不是所有盘都用内置引擎**：`RunClean` 对 ≤4KB 簇的盘仍走系统 defrag（`DefragEngine.cs:120-138`），阈值在这些盘上本来就不生效。所以门控是“降低误导”，不是“保证生效”。
- 门控只控制编辑，不丢数据：置灰时值照常保存，切回 Self 后不需要重填。引擎方式本身仍是下一次任务生效，不需要重启。

### 2.3 选项设计（表格）

| 名称 | 配置键 | 默认值 | 范围 | 生效阶段 | 对结果的影响 | 风险 |
|---|---|---|---|---|---|---|
| 只整理碎片率较高的文件 | `FragThresholdEnabled` / `FragThresholdPercent` | 关 / 10% | 开关；1–15% | 候选筛选 | 开：少而精，速度快、覆盖率低；关：所有满足硬条件的候选都处理 | 阈值高于实际碎片时几乎不选文件，看起来“没整理” |
| 最小处理文件大小 | `MinFileSizeKB`（新） | 32 KB | 4–4096 KB | 分析/候选筛选 | 调低显著提高覆盖率；实际按 `max(1 簇, 向上取整(KB/簇))` 折算。默认 32KB 在 4KB 簇上等价旧行为；在 64KB 簇上从 512KB 降到 32KB（1 簇），会多纳入大量文件 | 小文件数量多、单文件固定开销高，收益/耗时比下降；NTFS 常驻文件（数据在 MFT 记录内）本来就没有区段，仍无法整理 |
| 单轮最多文件数 | `MaxFilesPerRun`（新） | 40 | 10–500 | 规划/执行 | 直接决定一次任务能清理多少文件；调高比“反复跑”少一次扫描/复算的固定开销 | 单次任务变长；中断/休眠/电量风险上升；临时文件与备份的空间峰值不变，但连续写入更久 |
| 单轮最多数据量 | `MaxBytesPerRunGB`（新） | 8 GB | 1–64 GB | 规划 | 与文件数共同截断本轮；调高能纳入更大的文件，单文件超过上限会被跳过 | 耗时与磁盘占用时间线性增加；超大文件单独就吃掉全部额度 |
| 可回收空间下限 | `MinReclaimMB`（新） | 4 MB | 0–64 MB | 候选筛选 | 调低：更多“小碎片”文件进入候选，覆盖率更高；调高：只为大收益文件重写，速度更快 | 调得过低会为几百 KB 收益重读重写整个文件；0 表示不设下限（仍要求至少 1 个碎片簇） |
| 整理后校验 | `VerifyMode`（新） | `Auto` | `Auto` / `Full` / `Sample` | 执行（校验） | 不改变碎片结果，只改变速度与完整性保障。`Auto`=≤2GB 全量、>2GB 抽样（现状）；`Full`=全部全量；`Sample`=全部首/中/尾 4MB 抽样 | `Sample` 可能漏掉中段写坏；**不提供“不校验”**：`File.Replace` 成功后旧文件删除，写坏无法恢复 |

关于“最小处理文件大小”默认值：这会**有意改变**大簇盘行为（64KB 簇从 512KB 降到 32KB）。如果用户要求“升级后行为完全不变”，可把迁移默认设为“8 簇保持不变”，但覆盖率问题依旧存在。建议接受 32KB，并在迁移日志里写一行说明。

### 2.4 配置版本 5 → 6 迁移

现状：`ConfigStore.Load` 反序列化后只调 `Normalize()` 做范围回退（`ConfigStore.cs:33-52`），`ConfigVersion` 写了但没参与分支。方案：

1. `AppConfig.ConfigVersion` 默认改为 **6**。
2. 新增一个集中的迁移步骤（例如 `ConfigMigrations.Migrate(config, rawJson)`），在 `Load()` 里、`Normalize()` 之前调用：
   - `ConfigVersion < 6`：新键（`MinFileSizeKB`/`MaxFilesPerRun`/`MaxBytesPerRunGB`/`MinReclaimMB`/`VerifyMode`）**缺失才写默认值**；`FragThresholdEnabled`/`FragThresholdPercent`/`EngineMode`/`CpuThreshold` 原样保留；设 `ConfigVersion = 6`，写一条“配置已迁移到 v6”的日志。
   - 判断“缺失”用原始 JSON 属性名判断，而不是看字段值——否则无法区分“用户显式设成默认值”和“旧配置没这个键”。实现上可先 `JsonDocument.Parse` 一遍再反序列化。
   - `ConfigVersion > 6`（降级）：不回写、不覆盖用户值，只记日志“配置来自更高版本，未识别的键会被忽略”。
   - JSON 损坏：维持现状，整份回退默认值并写 `note`（`ConfigStore.cs:45-48`）。
3. `Save()` 保持“临时文件 + `File.Move` 原子替换”（`ConfigStore.cs:62-65`），并在 `Normalize()` 里补齐新键范围钳制。
4. **worker 兼容**：新 UI 通过 `WorkerService.BuildArguments` 追加 `--minfilekb/--maxfiles/--maxbytes-gb/--minreclaim-mb/--verify`；旧 UI 不传时 `WorkerHost` 必须回落到旧默认值（8 簇/40/8GB/4MB/Auto），保证行为不突变。参数解析后继续钳制范围，不信任外部输入。
5. 生效时机：与现有设置一致——下次整理开始时读取；保存后不重启 worker。预览/dry-run 也应读取同一组参数（否则预览数字和真实整理不一致）。

### 2.5 候选方向的取舍（哪些不做）

| 候选 | 判断 | 理由 |
|---|---|---|
| 最小处理文件大小 | **做** | 直接决定覆盖率，是当前最大的可见瓶颈 |
| 单次上限（文件数/数据量） | **做** | 单次任务只跑一批，40 文件决定了“一次能干净多少” |
| 可回收空间下限 | **做** | 4MB 硬门槛会把大量小碎片文件排除在外；调低是覆盖率杠杆 |
| 校验方式 | **做** | 不影响碎片，但直接影响速度/安全，是合理的“偏好” |
| 保留空闲空间比例 | 暂不做（可放高级第二期） | 现在是 0.5% 自动余量（`RewritePlanner.cs:70-71`），只在接近满盘时有意义；默认值调大容易造成“空间不足”跳过 |
| 系统盘用户数据 / 跳过某些目录 | **不做** | 现有分析已跳过系统目录；反向开放系统目录会撞上权限、占用、杀软，收益低风险高；自定义排除列表 UI 成本高，不如用磁盘勾选 |
| 优先整理碎片最多的文件 | **不做** | 已经是现状：`Score` 先按碎片簇+区段收益排序（`RewritePlanner.cs:59-63, 131-137`）。再给开关只是噪音 |
| 预分配/影响分配位置 | 不做开关 | 已用 `SetLength` 预分配（`RewriteExecutor.cs:271`）；是否连续由 NTFS 决定，用户无从控制 |
| 并行整理多个文件 | 不做 | 单盘并行会加剧随机 I/O 和临时空间竞争，碎片反而更多 |

## 3. 需求二：能不能达到 Defraggler 同级

### 3.1 数据文件最多能做到什么

**能做的**：

- 对**被选中的数据文件**，复制到新临时文件后由 NTFS 重新分配区段；只要卷上有足够的连续空闲，结果可以是 **1 个区段、文件级碎片率 0%**。
- 元数据（时间戳、ACL）会被快照并还原（`RewriteExecutor.cs:172-211`），不会因为重写丢属性。
- 校验（全量/抽样）能保证内容一致，失败会回滚。

**做不到的（物理/机制上限）**：

1. **整卷碎片率不会接近 0**。文件级重写只动被选中的文件；空闲空间仍是碎的，MFT、`$LogFile`、页面文件、休眠文件、正在使用的文件、系统保留区都不动。Windows 自带 `/X` 能合并空闲空间，但也有 HDD/10% 空闲门槛（`DefragEngine.cs:19-21, 345-390`）。
2. **重写后的文件仍可能再次碎片化**。新文件在旧文件仍占位时创建，NTFS 只能“就地找空”，空闲越碎，新文件越容易拿到多段。没有空闲空间整理，就无法保证连续。
3. **覆盖率限制**。默认一次 40 文件/8GB，分析有 90 秒/20 万文件/2 万次 Runlist 查询上限；覆盖率 = 已分析簇/卷总簇（`VolumeAnalyzer.cs:187-194`），小范围预览时可能只有 0.01%。Defraggler 是整卷扫描，两者数字不可直接比。
4. **常驻文件、稀疏文件、系统锁定文件**。常驻文件数据在 MFT 记录里，没有独立区段，文件级重写无从下手；稀疏文件被排除（`RewritePlanner.cs:114`）；被占用的文件预检会跳过。
5. **无法指定物理位置**。Defraggler 能做“把文件搬到盘首/合并空闲”，我们只能让 NTFS 自由分配，不能控制落点。

**结论**：在 HDD、空闲≥15%、数据以普通用户文件为主的前提下，**“被整理过的文件”可以做到 Defraggler 同级甚至更干净**；**“整卷报告数字”和“空闲空间碎片”做不到同级**。要把“接近 0”写进目标，必须先定义口径：按文件级区段数，还是按整卷碎片率。

### 3.2 缺口能力与取舍

| 能力 | 现状 | 收益 | 风险/成本 | 建议 |
|---|---|---|---|---|
| 小文件纳入整理 | 8 簇以下跳过 | 覆盖率明显提升；小文件碎片也是真实碎片 | 单文件固定开销高；常驻文件仍无解 | P1 作为设置项 |
| 预分配影响分配位置 | 已 `SetLength` | 减少临时文件自身碎片 | `SetFileValidData` 可省清零但需特权、可能暴露旧数据 | 保持现状，不做开关 |
| 近似合并空闲空间 | 无（系统方式才有 `/X`） | 让重写后的文件更容易连续；整卷数字更接近 Defraggler | 需要提权、耗时长、会移动大量数据；SSD 无意义 | P3，仅 HDD、可选、限时 |
| 按目录优先整理 | 无（按 Score 全局排序） | 同目录文件连续，局部碎片观感更好 | NTFS 不保证物理相邻，收益不确定 | 不做 |
| 启动期整理系统文件 | 无 | 能处理页面文件/注册表等锁定文件 | 需要驱动/启动阶段原生实现，蓝屏与数据损坏风险极高 | **不做** |
| MFT/元数据整理 | 无 | 元数据碎片对超大目录有意义 | 需要直接操作 `$MFT`，一错全盘报废；Windows 自带也只做有限处理 | **不做** |
| 多轮连续整理 | 无（一批即结束） | 同样时间下把候选清空，减少重复扫描的固定开销 | 任务不可控变长；需要停止/电量/时间上限 | P2 作为“整理强度”，不是无脑循环 |
| 整卷碎片率统计 | 只有分析子集口径 | 让用户能和 Defraggler 对数 | 整卷枚举慢、需要读卷位图/USN，统计口径复杂 | P2/P3，先统一口径再展示 |

### 3.3 速度优化点

| 优化 | 现状 | 预期收益 | 风险 | 阶段 |
|---|---|---|---|---|
| 提高单轮文件数/数据量 | 40 / 8GB | 减少“反复跑”的扫描+复算固定开销；同样总工作量下更快完成 | 单次任务变长 | P1（设置项） |
| 多轮整理 | 无 | 一次任务清空候选，减少重复分析 | 需要时间/轮次上限与停止检查 | P2 |
| 复制/校验缓冲 1MB → 4MB | 1MB（`RewriteExecutor.cs:274, 310`） | NVMe 上减少调用次数；HDD 提升有限 | 内存占用略增 | P2 |
| 校验阈值可调 | 2GB 以上抽样 | 大文件省一次全量读；CPU 哈希开销下降 | 完整性保障变弱 | P1（设置项） |
| 复用扫描结果 | 每次任务重新 Analyze | 连续整理时省 90 秒级扫描 | 需要缓存失效策略（USN/时间戳），实现复杂 | P3 |
| 减少 Runlist 查询 | 候选阶段逐文件查，上限 2 万 | 降低分析 CPU/IO | 不查就无法按碎片排序，收益有限 | 不做 |
| 并行重写 | 无 | 理论吞吐提升 | 单盘随机 I/O、临时空间竞争、碎片更差 | **不做** |
| 只校验写入部分 | 已按文件全量（≤2GB） | 按区段校验几乎不可行（NTFS 分配未知） | 实现复杂、收益小 | 不做 |

### 3.4 明确不建议做

1. **启动期系统文件整理 / boot-time defrag**：需要内核驱动或启动前原生程序，失败代价是全盘/无法开机；收益是页面文件、注册表等少数文件。
2. **直接操作 `$MFT`、绕过 NTFS 写卷**：任何实现缺陷都可能造成目录损坏；也不属于“整理设置”能兜住的风险。
3. **`SetFileValidData` 跳过清零**：需要 `SeManageVolumePrivilege`，且会把磁盘上残留数据暴露给目标文件，安全上不可接受。
4. **强制重写在用文件/页面文件/休眠文件**：只能靠重启前替换或驱动，风险与收益不匹配。
5. **并行重写同一块盘**：会制造更多碎片，和“整理”目标相反。
6. **提供“不校验”**：`File.Replace` 后旧文件删除，静默写坏无法恢复；这是数据安全问题，不是性能偏好。
7. **SSD 上做文件级重写**：SSD 没有寻道成本，重写只增加写入磨损；应按介质直接走系统 `/O` 优化（见 P2 的介质判断）。
8. **自定义目录排除列表**：UI 与维护成本高，且现有系统目录跳过已覆盖主要风险；用磁盘勾选更安全。

### 3.5 分阶段优先级

工作量用 S/M/L 表示（相对规模，不是工期承诺）。

| 阶段 | 目标 | 主要内容 | 工作量 | 风险 | 验收方式 |
|---|---|---|---|---|---|
| **P1 设置与迁移** | 让用户能控制覆盖率与单次整理量 | 新增分组与门控；迁移阈值；5 个新键 + 配置 v6；worker 参数链路；日志打印本轮参数 | M | 低–中（行为变化集中在覆盖率） | 旧配置升级后字段正确、阈值不丢；非法值不保存；dry-run 的候选数/覆盖率随 `MinFileSizeKB`、`MinReclaimMB` 变化；`last_result` 记录本轮参数 |
| **P2 整理量与速度** | 一次任务清得更干净，速度不劣化 | 多轮整理（带轮次/时间/停止上限）；复制/校验缓冲 4MB；按介质跳过 SSD 重写；把覆盖率与整卷口径分开展示 | M | 中（任务时长、停止语义） | 同一 10GB 样本：P2 前后总耗时与每文件区段数对比；停止后无残留临时/备份文件；SSD 不产生重写 |
| **P3 空闲空间合并（仅 HDD）** | 让整卷数字更接近 Defraggler | 重写结束后可选调用提权 `defrag /X`（仅在 HDD、空闲≥10%、用户勾选时）；失败不影响重写结果 | L | 中–高（提权、耗时、可能移动大量数据） | 合并前后空闲碎片/整卷碎片率对比；中断后卷仍可用；日志与 `last_result` 区分“重写”和“空闲合并”两段 |
| **不做** | — | 启动期系统文件、MFT/元数据、绕过 NTFS、并行重写、关闭校验 | — | 极高 | — |

### 3.6 建议的“同级”验收口径

不要用单一“碎片率 %”验收，建议同时看：

1. **文件级**：被重写文件中 ≥95% 的区段数 ≤2（目标 ≤1 的比例越高越好）。
2. **覆盖**：一次任务实际处理的数据簇 / 卷总簇；配合 P2 多轮，目标 ≥50% 数据簇。
3. **整卷（仅 HDD，P3 后）**：空闲空间碎片与整卷碎片率；没有 `/X` 时不承诺接近 0。
4. **速度**：同一 10GB 文件集，总耗时不超过 Defraggler 的 1.2 倍；每 GB 的读写放大不超过 3 倍（读源+写临时+校验读）。
5. **安全**：0 内容损坏、0 属性丢失、停止/断电后无半成品残留（现有回滚与备份机制需继续保留）。

## 4. 风险与待确认

1. **默认值变化**：`MinFileSizeKB=32` 会让 64KB 簇盘从 512KB 门槛降到 32KB，覆盖率上升但耗时增加；是否接受这次行为变化？
2. **Auto 是否置灰**：本文建议置灰（与用户倾向一致）；若希望“先调好、以后切 Self 直接用”，也可改成“可编辑但整组加黄色提示”。两种都能实现，推荐置灰。
3. **P3 的 `/X` 合并**：需要提权与较长耗时，是否愿意作为可选开关（默认关）？
4. **覆盖率展示**：当前 `last_result` 与界面只给碎片率，容易误读为整卷；是否在 P2 增加“覆盖率 X%”一行？
5. **SSD 大簇盘**：现在大簇盘会走文件级重写，不看介质；P2 建议按介质跳过（SSD 直接 `/O`），需要确认大簇 SSD 的实际场景。

## 6. 1.5.0 实现记录（P1 + P2 + 整理质量三档）

> 本节记录已落地的实现与实测证据，数值以发布版 `publish/AutoDefrag.exe`（1.5.0）为准。

### 6.1 整理质量三档参数表

| 参数 | 最快 Fast | 均衡 Balanced（默认） | 最彻底 Thorough |
|---|---|---|---|
| 最小处理文件 | 256 KB | 32 KB | 4 KB |
| 单轮最多文件数 | 20 | 80 | 300 |
| 单轮最多数据量 | 4 GB | 16 GB | 32 GB |
| 单文件可回收下限 | 16 MB | 4 MB | 1 MB |
| 碎片率阈值 | 开启，10% | 关闭（保留 10%） | 关闭（保留 5%） |
| 整理后校验 | 抽样（首/中/尾各 4MB） | 自动（≤2GB 全量，超过抽样） | 全量 SHA256 |
| 多轮上限 | 1 轮 | 3 轮 | 8 轮 |
| 任务总时长上限 | 30 分钟 | 120 分钟 | 480 分钟 |
| 固态只做系统优化 | 开（独立开关，不参与档位判定） | 开 | 开 |

门控：整理方式 = 本程序整理时可编辑；Windows 自带整理 / 自动时整组置灰并显示原因，已保存值不丢。参数与某档完全一致时显示该档名称；手动改动任一项后显示「自定义」，改回完全一致的数值时档位与单选会同步恢复。`SsdOptimizeOnly` 是介质安全开关，不属于整理质量参数，改动不会把档位变成自定义。

### 6.2 数值依据与耗时差异

- **最快**：用“高碎片 + 大文件 + 高收益”三个门槛把候选池压到最小。256KB 门槛按 64KB 簇折算为 4 簇，仍能覆盖此前 512KB 门槛漏掉的中等文件；16MB 可回收下限保证不会为一个几百 KB 的零头重读整文件；10% 文件碎片率阈值复用旧语义。抽样校验只读 3×4MB，适合“先缓解卡顿”。总量 20 文件/4GB/1 轮/30 分钟，**预期单次 1–2 分钟量级**（按机械盘顺序 ~100MB/s、单文件读写+校验约 2.2 倍数据量估算：3.9GB × 2.2 ÷ 100MB/s ≈ 86 秒，另加分析）。
- **均衡**：默认档，目标是把旧版“单批 40 文件/8GB、只跑一轮”的覆盖翻倍并允许补扫。32KB 在 64KB 簇盘上是 1 簇（旧版 512KB=8 簇，这次门槛明显放宽），在 4KB 簇盘上是 8 簇，这是覆盖率提升的主要来源；16GB/80 文件是旧值的约两倍；3 轮在候选不足时提前结束。**预期单轮 6–8 分钟量级**（16GB × 2.2 ÷ 100MB/s ≈ 6 分钟），总时长上限 120 分钟兜底。
- **最彻底**：4KB 门槛（64KB 簇盘仍至少 1 簇=64KB，NTFS 最小分配单位决定下限）、1MB 可回收下限、300 文件/32GB、最多 8 轮、全量校验。**预期单轮 12–15 分钟量级**（32GB × 2.2 ÷ 100MB/s ≈ 12 分钟），多轮合计不超过 480 分钟；建议空闲时运行。全量校验会让读放大再增加约 1 倍数据量，这是“最彻底”慢于“均衡”的另一半原因。
- 三档都保留“不提供完全不校验”：`File.Replace` 成功后旧文件删除，静默写坏无法恢复。
- 分析阶段本身受 60 秒 / 1.5 万文件 / 1.2 万次 Runlist 上限约束，所以三档的“候选数”差异在测试卷上只有 30 多个，但**排除了多少小文件**差异明显：最快档排除 40,741 个“文件太小”，均衡/最彻底只排除 33,190 个。

### 6.3 已落地的 P1 参数与迁移

- 新键：`MinFileSizeKB` / `MaxFilesPerRun` / `MaxBytesPerRunGB` / `MinReclaimMB` / `VerifyMode` / `MaxRounds` / `MaxRunMinutes` / `SsdOptimizeOnly` / `DefragQuality`。
- `ConfigVersion` 5→6；读取时先按**原始 JSON 属性是否存在**判断缺字段，只给缺失键补默认，旧值（含 `FragThresholdEnabled`/`FragThresholdPercent`/`EngineMode`/`CpuThreshold`）原样保留；迁移后立即落盘。非法值按范围回落，不静默保留坏值。
- worker 参数链路：`--quality/--minfilekb/--maxfiles/--maxbytesgb/--minreclaimmb/--verify/--rounds/--maxminutes/--ssdopt`，解析后再做范围钳制；检查磁盘（status）不携带整理参数。
- 64KB 簇的最小门槛“可以降到 32KB”由均衡档采用；最快档用 256KB，最彻底档用 4KB。

### 6.4 已落地的 P2 行为

1. **多轮整理**：`LargeClusterRunner` 每轮重新 `RewritePlanner.Build`，受 `MaxRounds`、`MaxRunMinutes`、停止标记约束；候选不足或某轮零成功时提前结束，不会“只跑 40 个就结束”。
2. **复制缓冲 1MB→4MB**：`RewriteExecutor` 读写共用 4MB 缓冲，校验与复制使用同一套抽样口径。
3. **校验可调**：Auto/Full/Sample 三档，不提供关闭。
4. **SSD 分流**：`SsdOptimizeOnly=true`（默认）时，固态大簇卷不做文件级重写，实际整理走系统优化 `/O`；dry-run、真实整理、日志、进度区都明确说明“跳过文件级重写（避免写入磨损）”，不会让人误以为“点了没反应”。机械硬盘不受影响。
5. **覆盖率**：`CoveragePercent = 已分析簇 / 总簇 × 100`，在进度区、dry-run/整理报告、`last_result` 汇总中单独展示，并注明“碎片率只代表已分析文件，不是整卷”。
