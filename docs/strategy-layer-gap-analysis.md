# 方案 B 建议的差距分析与实施方案

> 状态：方案评估，未改代码、未构建、未发布、未推送 GitHub
> 评估对象：外部建议「放弃自研引擎，退回包装 defrag.exe + 策略层」
> 现行版本：AutoDefrag 1.9.0
> 结论摘要：**不换架构**；建议中 5 条采纳、3 条部分采纳；真正影响“整理彻底程度”的只有 2 条，其余属于工程卫生

---

## 0. 架构结论：不采纳方案 B

| 判断 | 理由 |
|---|---|
| 不放弃自研文件级重写 | 目标盘是 64KB 簇卷。系统 `defrag.exe` 在该卷上返回 0、几百毫秒结束，`FSCTL_MOVE_FILE` 在 >4KB 簇上不可依赖；退回方案 B 等于放弃唯一有效路径 |
| 保留系统 defrag 作为小簇路径 | ≤4KB 簇卷上系统整理工作正常，继续用 `/D`、`/O`、按门槛 `/X`，成本最低 |
| 吸收建议中的工程纪律 | 状态可证实、参数安全、解析降级、停止语义、测试矩阵，这些与是否自研无关，应该做 |

因此本文的定位是：**架构不变，补工程纪律**，并明确区分“能提高整理效果”和“只是让程序更可靠/更可维护”的两类改动。

## 2. 八条建议逐项评估

### 2.1 每卷独立策略与历史记录 —— 部分采纳（P1）

**建议内容**：卷标识、文件系统、容量、介质、上次分析/执行/结果、最近错误码。

**现状**：`drive_status.json` 字段太少，且只反映“探测”；执行结果只存在覆盖式的 `last_result.txt` 与报告里，无法回答“这块盘上次整理是什么时候、结果如何”。

**结论**：采纳数据结构，但**不新建文件**。扩展现有 `drive_status.json`（加 `SchemaVersion`），执行结束后由现有写出路径回填；`last_result.txt` 仍作为人类可读摘要，报告仍是明细。这样不产生第三套存储。

建议字段：

```
SchemaVersion, ProbeTime
Drives[]:
  Drive, VolumeSerial, FileSystem, ClusterBytes, Media,
  VolumeSizeGB, FreeSpaceGB,
  FragPercent, Probed,
  LastAnalyzeAt, LastRunAt,
  LastRunStatus, LastErrorCode,
  LastWinFragBefore, LastWinFragAfter,
  CoveragePercent, MergeStatus
```

要点：

- `VolumeSerial` 用于识别“同一个盘符换了盘”，避免把 A: 的历史套到新磁盘上；
- 旧文件没有 `SchemaVersion` 时按 v1 读取，缺字段为 null，不迁移、不清空；
- 历史只保留“最近一次”，不做无限追加；需要趋势时再看报告/日志。

**工作量**：1–1.5 人日（含旧文件兼容、UI 读取、报告关联）。
**影响类别**：工程卫生（让“为什么跳过/为什么延后”有据可查），不直接提高整理彻底程度。

---

### 2.2 分析 → 决策 → 执行 → 复查闭环 —— 采纳（P1）

**建议内容**：复查必然发生；状态只用可证实词；禁止“速度提升 X%”。

**现状**：

- `/A` 后测在小簇路径与自研路径都会跑，但“被停止/`/X` 失败”时后测会缺失；
- 状态词混用：“成功 / 部分成功 / 已停止 / 可能不支持 / 无法确认 / 跳过”；
- 代码与文档中未发现“速度提升 X%”这类表述（已检索），这条属于预防性约束。

**结论**：采纳，但要定义清楚“必然”：

1. 只要卷上发生过任何写操作，且任务不是被用户立即停止，就必须尝试一次 `/A` 后测；
2. 后测失败时状态不能是“已完成”，应降级为“已完成（复查失败）”并在报告写原因；
3. 统一状态枚举（6 个，比建议多一个“中断”）：

| 状态 | 含义 | 允许出现的前提 |
|---|---|---|
| 已完成 | 执行成功且复查成功 | 有 `/A` 后测或明确的“无法复查”原因 |
| 无需优化 | 未执行，且判定依据充分 | 见 2.3 的大簇例外 |
| 失败 | 有明确失败证据 | 非 0 退出码 / 错误码 / 校验失败 |
| 延后 | 条件不满足，未执行 | 记录延后原因（忙、电量、空间、间隔） |
| 已停止 | 用户停止，且当前操作已安全收尾 | 自研引擎“当前文件完成”；系统整理需按 2.7 改造后才可用 |
| 已中断（结果未知） | 进程被强制结束或卷状态无法确认 | 强杀、断电、卷被占用 |

4. 报告中“对外口径”永远是 `/A` 前后并列；“本程序口径”并列文件碎片率与覆盖率；禁止把“区段减少”换算成“速度提升”。

**工作量**：1.5–2 人日（状态枚举贯穿 worker、报告、UI、`last_result`）。
**影响类别**：一半是工程卫生（诚实），一半影响效果判断（没有复查就无法证明整理是否有效）。

---

### 2.3 自动决策规则保守可配置 —— 部分采纳（P1，但必须加例外）

**建议内容**：间隔过近跳过、系统忙延后、`/A` 显示无需整理则不执行、低电量/低磁盘处理。

**逐条结论**：

| 规则 | 结论 | 说明 |
|---|---|---|
| 距上次整理过近跳过 | 采纳 | 建议默认 20 小时；可配置；以 `LastRunAt` 为准，而不是“今天跑过没有” |
| 系统忙 / 任务已在跑延后 | 采纳 | 现在直接返回退出码 3；改为“延后”并记录原因，不当作失败 |
| `/A` 无需整理则不执行 | **部分采纳，必须加例外** | ≤4KB 簇卷可以；**>4KB 簇卷禁止**用 `/A` 的“不需要整理”抑制文件级重写——这正是系统分析失真的场景。大簇卷只能把 `/A` 当作展示与参考 |
| 低电量 | 采纳 | 用 `SystemInformation.PowerStatus`；电池供电且低于阈值（建议 40%）→ 延后；插电不限制。默认开启，可关 |
| 低磁盘空间 | 采纳 | 系统路径：空闲低于 `max(5GB, 3×预计写入量)` → 延后；自研路径已有逐文件空间检查，补充“整卷门槛”避免跑到一半失败 |
| 阈值来源说明 | 采纳 | 文档与设置提示中写明：20 小时、40%、5GB 等是产品默认值，不是行业标准 |

**工作量**：1.5–2 人日（含配置项、UI 提示、状态联动）。
**影响类别**：主要是工程卫生与可靠性；唯一影响效果的是“`/A` 无需整理”这条——必须按簇大小分流，否则会误伤大簇盘。

### 2.4 `/X` 从每日自动改为手动高级操作 —— 采纳（P1）

**建议内容**：移出每日任务，手动触发，执行前给耗时预期与“不保证提速”。

**现状**：`MergeFreeSpace` 默认 `true`，自动任务在门槛满足时直接跑 `/X`；大容量机械盘上这一步可能耗时很长。

**结论**：采纳，但保留三件事：

1. 仅 HDD、门槛判断、失败识别全部保留；
2. 自动任务不再触发 `/X`；手动入口给“预计耗时”区间（按已用数据量/历史吞吐估算，明确标注“估算”）；
3. 配置兼容：新增独立字段（例如 `MergeFreeSpaceMode = Auto/Manual/Off`），旧 `MergeFreeSpace=true` 映射为 `Manual`，不丢用户选择；默认新用户 `Manual`。

**取舍必须写清**：`/X` 是改善“空闲空间碎片”的唯一杠杆；移出自动任务意味着每日整理不再自动改善它，需要用户主动点。对“希望 `/A` 更低”的用户，应在报告与界面明确提示“可手动执行空闲合并”。

**工作量**：1 人日（配置迁移 + UI + 报告文案）。
**影响类别**：产品策略；对“文件碎片彻底程度”无直接影响，对 `/A` 的空闲空间部分有潜在影响。

### 2.5 进程与参数安全 —— 部分采纳（P2）

**建议内容**：`ArgumentList` 逐项传参、卷路径严格校验、不拼命令行。

**现状**：`WorkerService` 拼 `Arguments` 字符串；`WorkerHost` 按分隔符切分；`--datadir` 也是拼接。盘符来自 UI/配置，风险不高，但属于低成本硬化。

**结论**：采纳以下部分：

- `ProcessStartInfo.ArgumentList` 逐项添加（.NET 会自动处理引号与空格）；
- worker 端严格校验：只接受 `^[A-Za-z]:$`，拒绝 UNC、相对路径、带斜杠、多字符；
- 未知参数忽略并记日志，不因拼写错误改变行为；
- `--datadir` 仍允许路径，但校验为绝对路径且存在，失败回退默认目录。

不采纳“完全禁止用户可控字符串”：`--datadir` 与盘符列表本身就是用户/配置可控，关键是校验与逐项传递，而不是消灭输入。

**工作量**：0.5 人日。
**影响类别**：工程卫生（安全与可维护性）。

### 2.6 本地化与解析 —— 部分采纳（P1）

**建议内容**：不能靠解析系统输出决定策略；必须解析的内容做版本/语言适配；退出码映射独立模块。

**现状**：

- `/A` 解析先找英文 `fragmented space`，找不到就用“任意百分比”兜底；中文输出依赖 OEM 代码页；
- 错误码用正则提取 `0x89xxxxxx`；
- 退出码判断散落在 `ClassifyResult` 等方法里。

**结论**：采纳，原则改成三句话：

1. **策略不依赖文本**：自研分析用 FSCTL，不解析文本；“是否需要整理”只由结构化的簇大小、`/A` 数值（可为未知）、空闲空间决定；
2. **解析失败必须降级为“未知”，不能降级为“0%”或“无需整理”**；未知时不触发自动跳过，除非用户显式选择“信任系统报告”；
3. 抽出 `DefragExitCodes` 模块：退出码、`0x89000024`（权限）、`0x89000000`（卷忙）统一映射；`/A` 解析增加中英文样本的单元测试（含“总碎片空间 = 9%”与“Total fragmented space = 9%”）。

**工作量**：1 人日（含测试样本）。
**影响类别**：工程卫生 + 决策正确性；不改变单文件搬移效果。

### 2.7 停止语义（重点）—— 采纳改造建议（P0）

**核实结果**：当前实现对系统 `defrag.exe` 的处理是：

```
检测到停止标记
  → 若处于挂起状态，先 NtResumeProcess
  → process.Kill(entireProcessTree: true)
  → stopped = true
  → 最终状态写“已停止”
```

涉及 `DefragEngine.cs` 的 `RunOneDrive` 与 `MonitorProbe` 两处；`/A` 预检与 `/D`、`/X` 共用同一逻辑。

**强杀的实际后果（能确认与不能确认的）**：

| 事项 | 判断 |
|---|---|
| 卷/文件系统损坏 | 不能从代码证明会发生。NTFS 有日志与原子元数据更新，用户态进程被杀通常不会造成结构损坏；但这不是微软支持的停止方式，极端时点无法排除需要 `chkdsk` |
| 当前文件搬移是否完成 | **无法确认**。`FSCTL_MOVE_FILE` 是内核侧操作，进程被杀后该文件可能已在新位置，也可能仍在旧位置；两种都不算损坏，但“整理了多少”不可知 |
| 卷是否立即可用 | 不保证。实测遇到过后续 `/A` 返回 `0x89000000`（卷上有操作进行中），需要等待 |
| 进度/结果 | 丢失。被杀后没有完整输出，`/A` 后测通常也不会再跑 |
| 把状态记成“已停止” | **不准确**。它掩盖了“当前卷结果未知”这一事实，属于必须修的诚实性问题 |

**自研引擎的停止语义复核**：

- 停止标记只在“开始下一个文件前”检查；当前文件会走完复制→校验→替换→复核；
- 不会中途杀自己的线程，也不会留下半写文件；
- 报告状态“已停止”，并统计已完成/失败/跳过；
- 结论：**自研引擎的停止语义是正确的**，不需要改成“中断”；只需在文案上写清“当前文件已完成，未开始的文件未处理”。

**建议改法（分介质/操作分级）**：

| 操作 | 建议停止方式 | 状态 |
|---|---|---|
| `/A` 只读预检 | 可直接结束进程（只读，无副作用）；若被挂起先恢复 | 已停止 |
| 小簇卷 `/D` | 写停止标记后**不杀**；不再启动后续卷；等待当前 `defrag` 自行结束；界面显示“正在停止，等待当前卷完成” | 已完成当前卷则“已停止”；超过等待上限仍未结束则“已中断（结果未知）” |
| 小簇卷 `/X` | 同 `/D`，但等待上限更长；由于 `/X` 改为手动操作，用户在场，优先“等它自己结束” | 同上 |
| 用户强制结束 | 二次确认，明确提示“可能中断当前卷，结果未知” | 已中断（结果未知） |

**代价与风险**：

- 停止延迟从“立即”变成“当前卷剩余时间”，`/X` 可能很久；必须在 UI 上明确显示“正在等待当前卷结束”，并提供“强制结束（不推荐）”；
- worker 生命周期变长，托盘与单实例逻辑需要能显示“正在停止”；
- 如果用户直接任务管理器结束 worker，仍然回到“结果未知”，所以报告必须能识别“上次异常结束”（启动时发现 `worker_state.json` 的 `UpdatedAt` 很旧且无结束标记）。

**工作量**：2–3 人日（停止状态机、UI 文案、超时与强制路径、报告字段、异常恢复识别）。
**影响类别**：**工程卫生为主，但直接关系“结果可信”**；不改变整理彻底程度。

### 2.8 测试矩阵 —— 采纳为计划（P2）

| 场景 | 现有覆盖 | 缺口 | 建议验证 |
|---|---|---|---|
| HDD / 64KB 簇 | 有实机（A:）与真实重写 | 无自动化 | 固定测试目录 + 断言区段减少、哈希一致 |
| HDD / 4KB 簇 | 代码路径存在 | 缺实机证据 | 小容量 VHD（4KB 簇）跑 `/D`、`/X` |
| SSD / 4KB 簇 | 有 C: `/O` 实测 | 无 `/X` 拒绝断言 | 断言不执行 `/X`、不文件级重写 |
| SSD / 大簇 + 只优化 | 代码路径 | 缺实机 | VHD 模拟或跳过，仅单测分派 |
| 未知介质 | 分派为 Unknown → `/O` 保守 | 缺注入测试 | 单测注入介质枚举 |
| 低磁盘空间 | 自研逐文件检查 | 系统路径无整卷门槛 | 小 VHD 填满后跑，断言“延后/失败”而非“成功” |
| 无管理员权限 | UAC 取消有提示 | worker 内部权限失败未单测 | 取消提权、受限账户各一次 |
| 任务重复启动 | 单实例 + TaskGate | 无并发自动化 | 双开、UI 预览与整理并发 |
| 睡眠/关机中断 | 无 | 无恢复识别 | 运行中睡眠/强制关机，重启后看状态 |
| `/A` 输出语言 | 仅本机中文 | 无英文/异常样本 | 解析单测固定样本 |

**工作量**：2 人日（不含 VHD 环境准备）。
**影响类别**：工程卫生。

## 3. 建议采纳清单（含优先级与工作量）

| # | 条目 | 结论 | 优先级 | 工作量 | 影响类别 |
|---|---|---|---|---|---|
| 1 | 停止语义改造（不杀 `/D`、`/X`；状态改“已中断/结果未知”） | 采纳 | P0 | 2–3 人日 | 工程卫生（结果可信） |
| 2 | `/A` “无需整理”不得抑制大簇卷文件级重写 | 采纳 | P0 | 0.2 人日 | **影响彻底程度** |
| 3 | 进程参数改用 `ArgumentList` + 盘符严格校验 | 采纳 | P1 | 0.5 人日 | 工程卫生 |
| 4 | 退出码映射独立模块 + 解析失败降级为“未知” | 采纳 | P1 | 1 人日 | 工程卫生 + 决策正确性 |
| 5 | 统一 6 态结果词 + 复查强制执行 | 采纳 | P1 | 1.5–2 人日 | 一半影响效果判断 |
| 6 | `drive_status.json` 扩展每卷历史 | 采纳 | P1 | 1–1.5 人日 | 工程卫生 |
| 7 | `/X` 移出每日自动，改手动高级操作 | 采纳 | P1 | 1 人日 | 产品策略（影响 `/A` 空闲部分） |

## 4. 明确不采纳清单及理由

| 建议 | 结论 | 理由 |
|---|---|---|
| 放弃自研引擎，全面包装 `defrag.exe` | 不采纳 | 64KB 簇卷上系统整理返回 0 但不搬数据；这是本程序存在的理由 |
| 用 `/A` 的“无需整理”统一决定是否执行 | 不采纳（仅小簇可用） | `/A` 在大簇卷上失真；用它做闸门会直接降低整理彻底程度 |
| 为“完整感”引入新的历史数据库/服务 | 不采纳 | 现有 `drive_status.json` + 报告 + 日志足够；平行存储会增加不一致风险 |
| 把“区段减少”换算成“速度提升 X%” | 不采纳 | 无法从区段数推导真实吞吐；属于不可证实表述 |
| 停止时立即强杀所有 defrag 进程 | 不采纳（`/A` 除外） | 当前卷结果不可知，且状态会被错误记成“已停止” |
| 自动任务默认执行 `/X` | 不采纳 | 大容量机械盘耗时长，且“不保证提速”；改为手动并给预期 |

## 5. 影响分类：彻底程度 vs 工程卫生

**真正影响“整理彻底程度”的（用户核心诉求）**

1. `/A` 不得抑制大簇卷的文件级重写（第 2.3 条例外）；
2. 复查必须发生，否则无法证明整理是否有效、也无法据此调整下一轮策略；
3. 覆盖率/补扫/64KB 簇门槛已经是 1.9.0 的现状，本轮建议**没有**提出新的提高覆盖率手段。

**工程卫生（值得做，但不改变单文件搬移效果）**

- 每卷历史、状态词、参数安全、退出码模块、解析降级、停止语义、测试矩阵、`/X` 手动化。

> 结论：这份建议的主要价值是“让结果可信、让失败可解释”，不是“让碎片更少”。不要把它包装成后者。

## 6. 推荐路线

**第一阶段（P0，约 1 周内）**

1. 停止语义：`/D`、`/X` 不再强杀；状态区分“已停止 / 已中断（结果未知）”；
2. `/A` 无需整理的大簇例外；
3. 退出码模块与解析降级（与停止改造同批，避免二次改状态机）。

**第二阶段（P1，约 1–2 周）**

4. `ArgumentList` + 盘符校验；
5. 6 态结果词 + 强制复查；
6. `drive_status.json` 扩展历史；
7. `/X` 改手动 + 配置迁移。

**第三阶段（P2）**

8. 保守自动规则（间隔、忙、电量、空间）；
9. 测试矩阵与 VHD 验证。

**第一版最小改动集（建议先只做这 5 项，约 4–5 人日）**

1. `/D`、`/X` 优雅停止，状态“已中断（结果未知）”；
2. `/A` “无需整理”仅对 ≤4KB 簇生效；
3. `ArgumentList` + `^[A-Za-z]:$` 校验；
4. 退出码/错误码独立模块，解析失败 → 未知；
5. `drive_status.json` 增加 `LastRunAt / LastRunStatus / LastErrorCode`。

这 5 项不改整理算法，不改变 1.9.0 的覆盖率与补扫逻辑，风险可控；做完后再评估是否继续做 `/X` 手动化与自动规则。

## 7. 风险与待确认

- **停止延迟**：优雅停止会让“停止”按钮的响应从秒级变成“当前卷剩余时间”；需要产品确认可接受的上限（建议 `/D` 120 秒、`/X` 600 秒，超时转“已中断”）。
- **`/X` 默认值变更**：旧配置 `MergeFreeSpace=true` 如何映射（建议映射为“手动”，保留用户能力，不自动执行）。
- **大簇卷 `/A` 例外**：需要确认“≤4KB 才允许用 `/A` 闸门”是否与用户预期一致；这是本轮唯一直接关系彻底程度的开关。
- **测试环境**：4KB/64KB 簇 VHD、无管理员账户、低电量场景需要准备，否则第 8 条只能停留在单测。
